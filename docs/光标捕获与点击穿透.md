本文说明 Magpie 在缩放期间如何处理鼠标：为什么需要「光标捕获」，点击穿透为什么必须配合层叠顺序，以及多窗口同时缩放时会互相踩到哪些全局状态。修改 `Magpie.Core/CursorManager.cpp`、`ScalingWindow::_UpdateFocusStateAsync`、`SrcTracker::UpdateState` 之前请先读完本文。

## 一、基本模型

Magpie 不向源进程注入任何代码。缩放窗口是一个**独立的置顶窗口**，画面由它自己绘制，鼠标输入则靠两件事转发给源窗口：

1. **移动真实光标**：把光标从缩放坐标换算回源窗口坐标，再 `SetCursorPos` 过去；
2. **点击穿透**：缩放窗口设置 `WS_EX_TRANSPARENT`，让鼠标消息落到它下面的窗口。

这两点决定了后面所有问题：**光标位置由 Magpie 控制，但鼠标消息的接收者由窗口层叠顺序决定，Magpie 无法指定**。

### 光标捕获

「捕获」不是 `SetCapture`，而是一套状态（见 `CursorManager::_StartCapture` / `_StopCapture`）：

- 隐藏系统光标，改由 Magpie 在叠加层里按 `_cursorPos` 自己绘制；
- 把真实光标钉在源窗口的对应位置（`_ReliableSetCursorPos`）；
- 按缩放倍率调低系统鼠标速度，并按屏幕排布 `ClipCursor` 限制光标不跑到黑边或屏幕外。

进入捕获有三个前提，任一不满足就会退出捕获（此时系统光标会重新显示）：

| 前提 | 判定 |
| --- | --- |
| 缩放窗口在光标处未被遮挡 | `WindowFromPoint(..., clickThroughHost=false) == hwndScaling` |
| 源窗口在光标处未被遮挡 | 仅桌面复制（Desktop Duplication）需要判定，见 `NeedsSourceOcclusionCheck` |
| 光标不在缩放窗口的可调整边框上 | `IsEdgeArea(_lastCompletedHitTestResult)` |

### 点击穿透

`WS_EX_TRANSPARENT` 的语义是「命中测试时跳过这个窗口」，于是鼠标消息交给**该点最上面的、不是穿透态的窗口**。

由此得到一条硬约束：

> **源窗口必须在光标处位于其它窗口之上，否则点击会落到别的窗口上。**

多客户端场景（同一款游戏开多个窗口，位置互相重叠）时违反这条约束的表现很具体：**只有两个窗口重叠的那一小块矩形里点击会切换客户端**，其余区域正常。这正是 `CursorManager::_EnsureSourceNotCovered` 存在的原因——进入捕获后检查源坐标处最上面的窗口，若不是源窗口（或其子窗口），用 `SetWindowPos(hwndSrc, HWND_TOP, SWP_NOACTIVATE)` 把它抬到最前。抬升对用户不可见：源窗口本来就被全屏缩放画面盖住。

例外：覆盖源窗口的是**当前前台窗口**时不抢层级（否则会把用户正在用的窗口压到游戏下面），只记一条日志。

## 二、多窗口：捕获归属与让行

每个缩放窗口各有一个 `CursorManager`，但它们操作的是**同一份桌面全局状态**：

| 全局状态 | 谁来维护 |
| --- | --- |
| 系统光标可见性 | `g_hideSystemCursorCount`（引用计数） |
| 鼠标速度 | `g_cursorSpeedRefCount`（引用计数） |
| `ClipCursor` 裁剪区 | `g_clipCursorOwner`（同一时刻只有一个所有者） |
| 光标捕获归属 | `g_captureOwner`（同一时刻只有一个持有者） |

前两项天然可共享（引用计数），后两项是**互斥资源**，因此需要仲裁：

- `TryAcquireCapture`：光标捕获归属。持有者的窗口销毁时自动回收；500ms 内换手次数过多会被拒绝（`光标捕获换手过于频繁`），避免两个窗口互相抢；
- `ShouldYieldToSibling`：光标处若有另一个**置顶**的缩放窗口，本实例让行（既不隐藏系统光标也不改穿透），因为那个窗口才是用户看到的画面；
- `_SetClipCursor` / `_RestoreClipCursor`：非所有者不得写入，发现实际裁剪区被外部改过就放弃还原并**同时放弃所有者身份**，否则会一直按过期的缓存判断「不需要重设」。

`ClipCursor` 是整台桌面的唯一状态，Windows 在切换前台窗口时会自动清空它。任何「先读 → 改 → 再写回」的写法都必须校验期间的改动，`_ReliableSetCursorPos` 就是这么做的。

## 三、已知失败模式与对应的防护

| 症状 | 机制 | 代码中的防护 |
| --- | --- | --- |
| 光标变成系统箭头、不跟随，游戏收不到鼠标，切出切回才恢复 | 缩放窗口绘着光标（`_shouldDrawCursor`）但没有捕获（`_isUnderCapture`），源窗口收不到任何输入 | 回归哨兵（见下）；`_LogCaptureBlocked` 记录被哪条判定挡住 |
| 只有一小块矩形里点击会切到另一个客户端 | 捕获期间穿透，点击落到压在源窗口上的另一个窗口 | `_EnsureSourceNotCovered` 抬升源窗口 |
| 快速 Alt+Tab 后光标被钉在一小块区域里 | `_ReliableSetCursorPos` 期间 OS 清空了裁剪区，旧代码把 8ms 前的矩形写回 | 写回前校验裁剪区仍是自己的 1×1；`_RestoreClipCursor` 校验失败时清缓存并放弃所有权 |
| 切回游戏后短暂（0.4~1.2 秒）失去捕获 | shell 的 `ForegroundStaging` / `Windows.UI.Input.InputSite.WindowClass` 抢到前台，缩放窗口被降级置顶 | `SrcTracker::IsTransientForegroundWindow`：这类临时前台窗口不算焦点变化 |
| 游戏自己长期持有 `SetCapture`（鼠标锁定）时游戏内光标不响应 | 旧代码对「前台窗口捕获光标」直接 `return`，真实光标留在缩放窗口上 | 源窗口持有捕获时继续走正常流程，把光标搬进源窗口 |

### 回归哨兵

`CursorManager::_UpdateCursorState` 末尾有一段哨兵：当「源窗口在前台 + 光标由 Magpie 绘制 + 未捕获 + 不涉及叠加层」持续 1 秒时，记录一条 warn：

```
光标已由 Magpie 绘制但未进入捕获超过 1 秒，源窗口收不到鼠标输入（光标=(x,y)，源窗口=0x…，缩放窗口=0x…，点击穿透=…）
```

上述所有失败模式最终都收敛到这个状态，因此它相当于一个**在真实环境里持续运行的回归检测**，不依赖用户复现。如果你改动这块代码后这条日志开始出现，说明退化已经发生。

## 四、排查方法

默认日志级别是 info，只记录状态迁移和异常。需要更细的信息（每帧状态、层级变更细节）时设置环境变量后启动：

```bat
set MAGPIE_LOG_LEVEL=debug
Magpie.exe
```

常用关键字（`%LOCALAPPDATA%\Magpie\logs\magpie.log`，滚动保留 4 份 × 500KB）：

| 关键字 | 含义 |
| --- | --- |
| `光标已由 Magpie 绘制但未进入捕获` | 哨兵，出现了死区 |
| `未能进入光标捕获: <原因>` | 被哪条判定挡住（限流：相同原因 3 秒一条） |
| `进入光标捕获（<原因>）` / `退出光标捕获（<原因>）` | 捕获状态迁移 |
| `源窗口 0x… 被 0x… 覆盖，已将其置于最前` | 点击会落到别的窗口，已修正层级 |
| `光标裁剪区已被外部修改` / `临时 1×1 裁剪区已被外部修改` | `ClipCursor` 被 OS 或别的程序改动 |
| `源窗口焦点变为前台/后台` | 焦点迁移，随后会调整层级 |
| `焦点更新结束` | 层级调整结果；只在异常（源窗口在前台却不紧邻缩放窗口之前）时以 warn 记录 |
| `渲染循环中断` / `光标状态更新中断` | 渲染循环停摆，光标会冻结 |

## 五、修改这一块代码时的检查清单

- 引入新的「缩放窗口是否被遮挡」判定时，注意 **WGC/DWM/GDI 的画面里不包含其它窗口**，按源坐标判定遮挡会误伤；只有桌面复制需要判定。
- 判断「点击会落到谁身上」用 `WindowBelowScalingWindows`，不要用 `WindowFromPoint`：后者会把其它缩放窗口当成遮挡者。
- 写入 `ClipCursor` 前先确认自己是所有者；读改写之间必须校验期间是否被改动。
- 任何会改变窗口层级的操作（`SetWindowPos`、`DeferWindowPos`）都要考虑它和 `WS_EX_TRANSPARENT` 的关系：层级决定输入去向。
- 新增提前 `return` 的分支时，确认它不会留下「绘制了光标却没有捕获」的状态；必要时调用 `_LogCaptureBlocked` 说明原因，否则日志里只会留下一段无法解释的空白。

## 六、关于自动化测试

这部分逻辑依赖真实窗口层级、前台窗口切换时机和 DWM 合成状态，项目里没有（也难以搭建）单元测试环境：把这样的逻辑抽成纯函数会丢掉它真正要验证的东西。替代方案是本文第三节的哨兵——它在真实运行中持续验证「光标是否可用」这一唯一重要的不变量，比针对内部判定的单元测试更能发现退化。人工回归建议：

1. 单窗口缩放：光标进出画面、进出黑边、窗口模式拖动边框；
2. 同一游戏开 2~4 个窗口互相重叠，交替点击重叠区域，确认不串窗口；
3. 缩放期间快速 Alt+Tab 来回切换，确认光标始终跟随；
4. 缩放期间用 `Win+Tab`、任务栏切换、最小化/还原；
5. 每次改动后检查日志中不出现哨兵 warn。
